CASE 01

동시 등록 시 LOT 번호가 중복되던 문제

  • 동시성
  • 행 잠금
  • SELECT FOR UPDATE
  • INSERT ON CONFLICT
  • 채번
한 줄 요약 읽고 더해서 저장하던 채번 로직을 날짜별 채번 테이블 + 트랜잭션 내 SELECT FOR UPDATE로 바꿔, 동시에 등록해도 LOT 번호가 중복되지 않게 했습니다.
시기 2024.11 (입사 후 첫 코드 과제), 2025.03 생산 실적 LOT에도 같은 방식 적용

상황

  • 식품 제조사 MES에서는 원재료를 입고할 때마다 LOT 번호를 붙입니다. 어떤 원료가 어느 제품에 들어갔는지 추적하는 기준이라 절대 중복되면 안 됩니다.
  • 번호 형식은 구분-날짜-순번이고, 순번은 날짜가 바뀌면 0001부터 다시 시작합니다.
  • 현장에서 여러 명이 동시에 입고를 등록하면 같은 LOT 번호가 생기는 문제가 보고됐습니다.

원인

기존 코드는 채번 테이블에서 현재 값을 읽고 → 1을 더해 → 저장했습니다. 읽기와 저장 사이에 잠금이 없어, 두 요청이 거의 동시에 들어오면 같은 값을 읽었습니다. "같은 번호가 있으면 다시 만든다"는 방어 코드도 검사와 저장 사이에 간격이 있어 같은 이유로 막지 못했습니다.

시간  요청 A                 요청 B
 t1   현재 값 읽음 → 3
 t2                          현재 값 읽음 → 3   ← A가 아직 저장 전
 t3   4로 저장, ...-0004
 t4                          4로 저장, ...-0004   ← 중복

해결 과정

  • 1차 — DB 시퀀스: 중복은 사라졌지만, 날짜마다 0001부터 다시 시작해야 한다는 규칙을 지킬 수 없었습니다.
  • 2차 — 날짜별 채번 테이블 + 행 잠금: 날짜마다 한 행씩 현재 순번을 두고, 그 행을 잠근 채로 읽고 올리도록 바꿨습니다.
  • 여러 품목을 한 번에 입고할 때는 필요한 개수만큼 범위를 한 번에 예약합니다.
@Transactional
public List<String> nextNumbers(String prefix, int count) {
    String dateKey = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);

    // 1. 그날 첫 요청일 때만 행 생성 (동시에 만들어도 한 행만 남음)
    jdbc.update("INSERT INTO daily_seq (date_key, curr_val) VALUES (?, 0) " +
                "ON CONFLICT (date_key) DO NOTHING", dateKey);

    // 2. 행 잠금: 다른 트랜잭션은 이 트랜잭션이 끝날 때까지 대기
    int curr = jdbc.queryForObject(
            "SELECT curr_val FROM daily_seq WHERE date_key = ? FOR UPDATE",
            Integer.class, dateKey);

    // 3. 필요한 개수만큼 범위를 한 번에 예약
    jdbc.update("UPDATE daily_seq SET curr_val = ? WHERE date_key = ?",
            curr + count, dateKey);

    return IntStream.rangeClosed(curr + 1, curr + count)
            .mapToObj(n -> "%s-%s-%04d".formatted(prefix, dateKey, n))
            .toList();
}
방식중복 방지날짜별 0001 재시작비고
읽고 +1 후 저장 (기존)XO읽기와 저장 사이에 다른 요청이 끼어듦
DB 시퀀스 (1차)OX날짜 규칙을 따로 만들기 어려움
날짜별 채번 테이블 + FOR UPDATE (최종)OO같은 날 채번은 한 줄로 서서 처리됨

결과 · 검증

  • 동시에 입고해도 LOT 번호가 중복되지 않고, 날짜별 순번 규칙도 유지했습니다.
  • 이후 거래명세서 번호처럼 중복되면 안 되는 번호는 모두 잠금을 건 뒤 번호를 정하는 방식으로 만들었습니다.
  • 두 브라우저에서 동시에 입고를 등록하고 등록 버튼을 더블클릭해 요청을 거의 동시에 보내는 방식으로, 같은 번호가 다시 생기지 않는 것을 확인했습니다.

다시 한다면

  • 동시성 테스트를 먼저 만들겠습니다. ExecutorService와 CountDownLatch로 100개 요청을 동시에 보내고, 만들어진 번호가 모두 다른지 확인하는 테스트입니다.
  • 잠금 범위를 의식하겠습니다. 채번을 긴 트랜잭션 안에서 하면 잠금도 그만큼 오래 걸리므로, 채번을 끝부분에 두거나 내부 식별자는 시퀀스로 두는 방식도 검토하겠습니다.
  • 마지막 방어선으로 유니크 제약을 두겠습니다.

  • 수량 정합성
  • 트랜잭션 경계
  • 상태 전이
  • 취소 원복
한 줄 요약 주문량을 넘는 출하지시와 지시량을 넘는 출하를 비관적 락을 건 뒤 서버에서 차단하고, 출하·지시 연결을 한 트랜잭션으로 묶어 취소해도 수량이 어긋나지 않게 재설계했습니다.

상황

식품 제조사의 출하는 수주(고객 주문량) → 출하지시(이만큼 내보내라) → 출하(실제로 나간 양, 재고 차감) 세 단계로 이뤄집니다. 지켜야 하는 규칙은 하나입니다: 수주량 ≥ 지시량 합계 ≥ 출하량 합계. 한 수주를 여러 번 나눠 지시하고, 한 지시를 여러 번 나눠 출하하며, 중간에 취소·마감도 일어납니다. 예약 서비스의 정원 → 예약 → 이용, 재고형 서비스의 판매 가능 수량 → 주문 → 배송과 같은 구조입니다.

문제 (기존 구조)

  • 지시를 등록할 때 수주 잔량을 검사하지 않아, 주문량보다 많이 지시할 수 있었습니다.
  • 출하와 지시 완료가 따로 처리됐습니다. 출하 저장 뒤 화면이 완료 API를 한 번 더 호출했고, 두 요청 중 한쪽만 성공할 수도 있었습니다.
  • 지시를 취소해도 수주 연결이 남아 수주별 지시량이 틀리게 계산됐습니다.

해결

  • 잠금을 건 뒤 남은 양을 계산하고 차단: 화면 검사만으로는 두 사람이 동시에 남은 양을 보고 각각 지시하면 둘 다 통과합니다. 수주 행과 지시 헤더에 비관적 락을 건 뒤 남은 양을 계산해, 뒤에 온 요청은 줄어든 잔량으로 다시 검사됩니다.
  • 출하 저장과 지시 갱신을 한 트랜잭션으로: 화면이 두 번 호출하던 완료 API를 삭제하고, 검사 → 출하 저장 → 지시 연결 → 누적 출하량 갱신을 같은 트랜잭션에서 처리합니다.
  • 상태는 저장값을 최소화하고 수량으로 계산: 저장하는 상태는 진행 중 / 끝남 두 개만 두고, 화면 상태(출하 대기·부분 출하·출하 완료·마감)는 수량으로 계산합니다.
  • 취소하면 어디까지 되돌릴지 정하기: 출하 완료 지시의 출하를 취소하면 지시를 다시 열고, 마감 지시는 그대로 둡니다. 마감하면서 수주에 돌려준 양을 다른 지시가 이미 썼을 수 있기 때문입니다. 출하가 있는 지시는 취소할 수 없습니다.
@Transactional
public void registerOrder(Long salesOrderId, BigDecimal requestQty) {
    // 수주 행 잠금: 같은 수주에 대한 동시 지시는 순서대로 처리
    SalesOrder so = em.find(SalesOrder.class, salesOrderId, LockModeType.PESSIMISTIC_WRITE);

    // 진행 중인 지시는 지시량, 끝난 지시(완료·마감)는 실제 출하량으로 계산
    BigDecimal reserved = reservedQty(salesOrderId);

    if (reserved.add(requestQty).compareTo(so.getQty()) > 0) {
        throw new IllegalArgumentException("수주 미지시량을 넘어 지시할 수 없습니다.");
    }
    orderRepository.save(ShipmentOrder.of(so, requestQty));
}

검증

운영과 분리된 테스트 서버를 따로 띄우고, 화면을 실제로 클릭·입력하는 방식으로 확인했습니다.

다시 한다면

  • 수량 비교를 BigDecimal로 통일하겠습니다. 일부 비교가 실수형과 허용 오차로 되어 있어, 단위가 커지면 경계에서 틀릴 여지가 있습니다.
  • 동시성 검증을 자동 테스트로 남기겠습니다. 같은 수주에 지시 두 건을 동시에 보내는 테스트가 있으면 잠금이 빠졌을 때 바로 알 수 있습니다.
CASE 03

삭제할수록 재고가 늘어나던 문제 (이력 기반 재계산)

  • 재고 정합성
  • 멱등성
  • 이력 기반 재계산
  • 파생값 관리
한 줄 요약 생산 차수를 삭제할 때 재고를 증감으로 되돌리던 방식을, 남은 소비 이력으로 다시 계산하는 방식으로 바꿔 몇 번 실행해도 결과가 같게 만들었습니다.
시기 2026.08

상황

  • 베이커리 MES에서는 한 작업지시를 여러 차수(회차)로 나눠 생산합니다. 차수마다 원재료·반제품 LOT를 투입하고, 투입한 양만큼 LOT 재고가 줄어듭니다.
  • 잘못 등록한 차수를 삭제하면 그 차수에서 쓴 양만큼 재고가 돌아와야 하는데, 쓴 양보다 더 많이 늘어나는 문제가 있었습니다.

원인

  • 기존 코드는 삭제할 때 현재 재고에 소비량을 더해서 되돌렸습니다. 그런데 투입 목록은 여러 차수가 함께 쓰는 목록이었고, 같은 LOT가 여러 행에 나올 수 있어 같은 소비량이 여러 번 더해졌습니다.
  • 더 근본적으로, 증감 방식은 한 번만 실행된다는 가정에 기대고 있어 중복 실행·부분 실패가 생기면 어긋난 값이 그대로 남습니다.

해결

재고를 저장된 값에 더하고 빼는 대상이 아니라, 소비 이력으로부터 계산되는 값으로 보기로 했습니다. 관련 LOT 번호를 중복 없이 모으고(Set), 차수의 소비 이력을 삭제한 뒤, 모은 LOT마다 남아 있는 소비 이력의 합계로 재고를 다시 계산합니다.

// 기존: 증감으로 되돌리기 — 같은 LOT가 두 번 나오면 두 번 더해짐
for (Input input : sharedInputs) {
    Lot lot = input.getLot();
    lot.setStock(lot.getStock().add(consumedQtyOf(batchId, lot)));
}

// 변경: 관련 LOT를 모아 두고, 삭제 후 이력으로 다시 계산
Set<Long> affectedLotIds = sharedInputs.stream()
        .map(Input::getLotId).collect(toSet());
consumptionRepository.deleteByBatchId(batchId);
affectedLotIds.forEach(this::recalculateStock);

계산현재 재고 ± 변화량입고량 − 소비 이력 합계
같은 처리가 두 번 실행되면두 번 반영됨결과 같음 (멱등)
이미 어긋난 값이 있으면그대로 남음계산할 때 바로잡힘
비용가벼움LOT마다 이력 합계 조회

결과 · 검증

  • 차수를 삭제해도 LOT 재고가 소비 이력과 항상 같게 맞고, 다른 차수가 함께 쓴 LOT도 남은 차수의 소비량만 빠진 상태로 정확히 계산됩니다.
  • 수동으로 재고를 되돌리던 코드를 없애 삭제 로직이 단순해졌습니다.
  • 삭제 전후의 LOT 재고를 소비 이력 합계와 비교해, 재고가 이력과 정확히 같아지는 것을 확인했습니다.

다시 한다면

  • 파생값을 저장할지부터 고민하겠습니다. 조회 성능 때문에 저장해야 한다면, 변경할 때는 항상 재계산하는 규칙을 처음부터 두겠습니다.
  • 정합성 점검 쿼리를 정기적으로 돌리겠습니다. 저장된 재고와 이력 합계가 다른 LOT를 찾는 쿼리를 두면, 다른 경로에서 생긴 어긋남도 빨리 발견할 수 있습니다.
CASE 04

금속검출기 데이터가 사라지던 문제 (TCP 메시지 경계)

  • TCP Socket
  • 메시지 프레이밍
  • 소켓 타임아웃 · keep-alive
  • 장애 추적 로그
  • 책임 분리
한 줄 요약 TCP에서 "한 번 읽은 것 = 메시지 하나"로 처리해 누락·오저장되던 금속검출기 데이터를, 수신 버퍼에서 형식이 완전한 메시지만 꺼내는 방식으로 바꿨습니다. 또 끊긴 연결 하나가 서버 전체를 막던 구조를 연결별 스레드·타임아웃·keep-alive·서버 소켓 자동 재시작으로 고치고, 단계별 지연 로그로 현장 문제를 추적했습니다.
시기 2026.04.27 ~ 2026.06.30

상황

  • 베이커리 공장의 금속검출기는 검사 결과를 TCP로 설비 서버에 보냅니다. 설비 서버는 결과를 DB에 저장하고, 조건에 맞으면 MES에 알림 이벤트를 보냅니다.
  • 금속 검출은 HACCP 중요관리점(CCP)이라 기록이 빠지면 안 되는 데이터입니다.
  • 현장에서는 검사를 했는데 기록이 비거나, 값이 이상하게 저장되거나, 어느 순간부터 데이터가 아예 안 들어오는 문제가 있었습니다. 개발 환경에서는 재현되지 않았습니다.

원인

  • TCP는 메시지 경계를 지켜 주지 않음: 기존 코드는 read() 한 번에 메시지가 정확히 하나 들어온다고 가정했습니다. 하지만 TCP는 바이트의 흐름이라 나눠서 오거나 붙어서 오고, 이어 붙이는 버퍼가 없어 잘린 메시지는 복구할 방법이 없었습니다.
  • 끊긴 연결 하나가 서버 전체를 막음: 연결 하나를 처리하는 동안 새 접속을 받지 않는 구조였고 읽기 타임아웃도 없어, 연결이 반쯤 열린 상태가 되면 장비가 다시 접속해도 받지 못했습니다.
  • 저장 실패와 알림이 따로 움직임: DB 저장이 실패해도 알림은 나갈 수 있었습니다.
장비가 보낸 것 :  [메시지 A][메시지 B]
한 번에 읽힌 것:  [A의 앞부분]          → 토큰 부족으로 버려짐 (누락)
               [A의 뒷부분][메시지 B] → 엉뚱한 위치의 토큰이 저장되거나 파싱 실패
               [메시지 A][메시지 B]   → A만 처리되고 B는 버려짐 (누락)

해결

  • 수신 버퍼 기반 메시지 추출: 읽은 바이트를 연결마다 버퍼에 쌓고 형식이 완전한 메시지만 꺼내 처리합니다. 덜 온 부분은 버퍼에 남겨 두었다가 다음에 읽은 바이트와 합칩니다. 시작 표식 검증과 정규식 형식 검사를 차례로 더해 자르는 기준을 엄격하게 했습니다.
  • 연결 유지와 자동 복구: 연결별 스레드로 끊긴 연결이 남아 있어도 새 접속을 받고, keep-alive로 사라진 연결을 감지하며, 서버 소켓 오류 시 5초 뒤 다시 엽니다. 읽기 타임아웃은 처음 5분으로 두었다가, 검사 간격이 5분을 넘기는 것이 정상인 현장 상황을 확인하고 2시간으로 늘렸습니다.
  • 단계별 지연 로그: 수신 대기·메시지 추출·분석·DB 저장·알림 처리 단계마다 기준을 넘을 때만 경고를 남겨, 어느 단계가 느려졌는지 로그만 보고 알 수 있게 했습니다.
  • 설비 서버와 MES의 책임 분리: 설비 서버는 수신·저장·알림 대상 판단·이벤트 전송만, MES는 패드·문자 알림과 이력 관리를 맡습니다. 알림은 DB 저장에 성공했을 때만 보냅니다.
StringBuilder buffer = new StringBuilder();          // 연결마다 하나

while ((len = in.read(bytes)) != -1) {
    buffer.append(new String(bytes, 0, len, UTF_8));
    extractMessages(buffer);
}

void extractMessages(StringBuilder buffer) {
    while (true) {
        Matcher m = MESSAGE.matcher(buffer);           // 시작 표식 + 7개 토큰 형식 검사
        if (!m.find()) {                               // 아직 완성된 메시지가 없음
            int last = buffer.lastIndexOf(START);
            if (last < 0) buffer.setLength(0);         // 시작 표식이 없으면 전부 버림
            else if (last > 0) buffer.delete(0, last); // 마지막 시작 표식부터만 남기고 기다림
            return;
        }
        if (m.start() > 0) {                           // 메시지 앞 찌꺼기 제거
            buffer.delete(0, m.start());
            continue;
        }
        process(m.group());                            // 형식이 맞는 메시지만 처리
        buffer.delete(0, m.end());                     // 처리한 만큼만 지우고 나머지는 다음 메시지로
    }
}

결과 · 검증

  • 메시지가 나눠서 오거나 붙어서 와도 완성된 메시지 단위로 처리하고, 형식이 맞지 않는 조각은 저장하지 않습니다.
  • 끊긴 연결이 남아 있어도 장비가 다시 접속할 수 있고, 서버 소켓 오류도 5초 뒤 스스로 복구합니다.
  • 2026.06 마지막 수정 이후 지금까지 데이터 누락이나 연결 끊김 문제 없이 운영되고 있습니다.

다시 한다면

  • 수신 파싱을 단위 테스트로 먼저 만들겠습니다. 메시지를 일부러 자르거나 붙여서 넣는 테스트가 있었다면, 현장에서 여러 번 고치기 전에 문제를 찾을 수 있었습니다.
  • 남은 버퍼의 상한을 두겠습니다. 일정 크기를 넘으면 버리고 로그를 남기겠습니다.
  • 스레드 관리를 스레드 풀로 바꾸고, 연결별 상태는 연결 객체에 두겠습니다.
  • 저장 시각 기준을 처음에 정하겠습니다. 장비 시계가 얼마나 믿을 만한지 먼저 확인했다면 처음부터 서버 수신 시각으로 정했을 것입니다.
CASE 05

7g씩 틀어지던 재고 (Float → BigDecimal)

  • 부동소수점 오차
  • BigDecimal
  • 단위 환산
  • 같은 원인 찾기
한 줄 요약 1,700만 g대 재고에서 입고 시 7g, 이동 시 1g씩 틀어지던 문제를, 창고·LOT·품목 재고 전체를 Float에서 BigDecimal로 전환해 해결했습니다.
시기 2025.05 첫 발견(LOT 재고 조정), 2026.11 재고 전체 전환

상황

  • 원물을 파레트 단위로 입고하는 식품 제조사에서는 재고를 g 단위로 저장합니다. 창고 재고가 수천만 g(수십 톤)까지 쌓입니다.
  • 재고가 1,700만 g대에 이르자, 입고하면 7g, 이동하면 1g씩 재고가 틀어지는 문제가 생겼습니다.

원인

  • DB 컬럼은 numeric이었지만, 자바 엔티티가 재고를 Float로 받아 계산했습니다.
  • Float은 유효숫자가 24비트라 16,777,216(2²⁴)을 넘는 정수는 모두 정확히 표현하지 못합니다. 그 이상에서는 1g 단위가 반올림됩니다.
  • kg를 g로 바꿀 때 Float으로 곱한 뒤 정수로 버림하는 코드까지 있어 1g이 더 빠질 수 있었습니다.
float stock = 17_000_001f;
System.out.println(stock == 17_000_000f);   // true → 1g이 사라짐
// 2²⁴ ~ 2²⁵ 구간에서 Float은 2 간격의 값만 표현할 수 있음

해결 과정

  • 2025 — 처음 발견하고 부분만 고침: LOT 재고를 조정하면 미세한 소수점 잔량이 남는 문제를 BigDecimal 계산으로 고쳤습니다. 같은 위험이 곳곳에 있을 것을 알았지만 변경 범위가 커서 그 화면만 고쳤습니다.
  • 2026 — 재고 전체 전환: 창고 재고·LOT 재고·LOT 소비·품목 재고의 수량 필드를 BigDecimal로 바꿨습니다. DB 컬럼은 이미 numeric이라 스키마 변경은 없었습니다.
  • 입고·출고·이동·출하·재고조정·포장 등 재고가 바뀌는 계산 경로에서 floatValue() 변환을 없애고, 재고 부족 비교도 compareTo로 바꿨습니다.
  • kg → g 환산은 BigDecimal로 계산해 정수 g로 반올림하고, 아직 Float인 엔티티와 만나는 곳은 변환 유틸 한 곳으로 모았습니다.
// 기존
long grams = (long) (kg * 1000f);                  // Float 오차 + 버림
lot.setStock(lot.getStock() + (float) grams);

// 변경
BigDecimal grams = kg.multiply(BigDecimal.valueOf(1000))
                     .setScale(0, RoundingMode.HALF_UP);
lot.setStock(lot.getStock().add(grams));
if (lot.getStock().compareTo(BigDecimal.ZERO) < 0) throw new IllegalStateException("재고 부족");

결과 · 검증

  • 1,700만 g대 재고에서도 g 단위까지 정확히 증감됩니다.
  • 한 화면만 고치던 2025년과 달리, 같은 원인이 남은 곳을 모두 찾아 고쳤습니다. 이 경험 뒤로는 문제를 하나 고치면 같은 원인이 남은 곳까지 함께 찾아봅니다.
  • 입고·이동 등 재고가 바뀌는 처리를 여러 번 반복해 테스트하며, 매번 g 단위까지 정확히 맞는지 검증했습니다.

다시 한다면

  • 처음부터 돈·수량에 Float을 쓰지 않겠습니다. 정확해야 하는 값은 BigDecimal이나 최소 단위 정수(g, 원)로 저장하고, 화면에서만 kg로 바꿉니다.
  • 기준을 코드로 막겠습니다. 수량 필드에 Float을 쓰지 못하게 하는 정적 분석 규칙이나 리뷰 항목을 두겠습니다.
CASE 06

포장기 누적 카운터를 기록으로 바꾸기 (Modbus TCP)

  • Modbus TCP
  • PLC 레지스터
  • 누적 카운터
  • 변화 감지
  • 장애 로그
한 줄 요약 삼면포장기 PLC가 들고 있는 누적 카운터를 Modbus TCP로 5초마다 읽어, 값이 늘었을 때만 저장하고 서버가 재시작해도 기준값을 이어 가도록 만들었습니다. 장비 리셋으로 값이 줄면 저장하지 않고 기준값만 다시 잡습니다.
시기 2025.10.24 ~ 2026.04.28

상황

  • 삼면포장기는 포장할 때마다 PLC 안의 카운터 값이 1씩 올라갑니다. 이 값은 장비가 보내 주는 것이 아니라, 서버가 Modbus TCP로 PLC 레지스터를 직접 읽어야 얻을 수 있습니다.
  • 카운터는 "이번에 몇 개를 포장했는지"가 아니라 지금까지의 누적 값이고, 장비를 리셋하면 다시 작은 값부터 시작합니다.

고려한 문제

  • 카운트가 어느 레지스터에 있는지 모름: 사양 문서가 없어 주소부터 찾아야 했습니다.
  • 누적 값을 그대로 저장하면 생기는 문제: 포장하지 않는 동안에도 같은 값이 쌓이고, 서버가 재시작하면 직전 값을 잊으며, 장비를 리셋하면 수량이 거꾸로 계산될 수 있습니다.
  • 장비가 꺼져 있을 때의 로그: 5초마다 같은 통신 오류 로그가 계속 쌓였습니다.

해결

  • 주소 탐색: 정해진 범위의 레지스터를 주기적으로 모두 읽고 값이 바뀐 주소만 로그로 남기는 기능을 먼저 만들어, 포장기를 돌리면서 같이 올라가는 주소를 찾았습니다.
  • 늘었을 때만 저장, 기준값 이어 가기: 서버 시작 시 DB의 마지막 값을 기준값으로 불러오고, 값이 줄면 리셋으로 보고 기준값만 다시 잡습니다.
  • 장애 로그 정리: 통신 실패는 처음 한 번만 경고로 남기고, 다시 연결되면 복구 로그를 한 번 남깁니다.
  • MES에서 검사별 포장 수량으로 바꾸기: 금속검출 검사 후 처음 읽은 값을 기준값으로 잡고 현재 값 − 기준값을 포장 수량으로 보여 주며, 실제 수량과 다르면 작업자가 직접 고칠 수 있게 했습니다.
private volatile int previousCount = -1;

@PostConstruct
void init() {                                    // 재시작해도 기준값을 이어 감
    repository.findLatest().ifPresent(last -> previousCount = last.getCount());
}

@Scheduled(fixedDelay = 5_000)
void poll() {
    int current = readCounterFromPlc();          // 실패하면 -1
    if (current < 0) return;

    if (previousCount < 0) {                     // 기준값이 없으면 세팅만 하고 저장하지 않음
        previousCount = current;
        return;
    }
    if (current > previousCount) {               // 늘었을 때만 저장
        repository.save(new CountRecord(current, LocalDateTime.now()));
    } else if (current < previousCount) {        // 줄었으면 리셋으로 보고 기준값만 갱신
        log.warn("카운터 감소 {} → {} (리셋 가능)", previousCount, current);
    }
    previousCount = current;                     // 같으면 아무것도 하지 않음
}

결과 · 검증

  • 포장하지 않는 동안에는 저장하지 않아, 실제로 포장한 순간만 기록으로 남습니다.
  • 서버를 재시작해도 DB의 마지막 값을 기준으로 이어서 읽고, 장비가 꺼져 있어도 경고 로그는 한 번만 남습니다.
  • 금속검출 검사마다 포장 수량이 자동으로 채워져 일지에 남습니다.
  • 현장에서 포장기를 직접 돌리며, 실제로 포장된 수량만큼 화면의 수량이 늘어나는 것을 확인했습니다.

다시 한다면

  • 누적 값과 함께 증가량도 저장하겠습니다. 증가량을 저장하면 리셋 전후를 따로 처리하지 않고 합계만 구하면 됩니다.
  • 리셋 직전의 수량을 놓치지 않게 하겠습니다. 리셋 이벤트를 따로 기록하는 방식을 검토하겠습니다.
  • 레지스터 범위를 확인하겠습니다. 레지스터 하나(16비트)로 읽고 있어 65,535를 넘으면 0으로 돌아갑니다.
  • 여러 대를 받을 수 있게 하겠습니다. 포장기가 늘어나면 장비별로 기준값을 따로 두어야 합니다.
